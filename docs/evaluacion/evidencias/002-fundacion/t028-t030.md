## Aceptación individual

- **T028 completada:** matriz SQL ampliada antes de habilitar listados. Admin A/B,
  barbero A/B, compartido admin A/barbero B, cliente sin membresía, inactivo y anónimo.
  Lectura propia incluso inactiva, permisos contextuales, cero perfiles ajenos y denegación
  de INSERT, DELETE y UPDATE de rol/estado/ambas FK, incluso para administradores.
- **T029 completada como preparación de pruebas:** `cases.mjs` define **342 casos** con
  IDs estables y expectativas: nueve actores × dos tenants × 19 operaciones. Las siete
  identidades autenticadas son sintéticas, con JWT emitidos por Auth local y metadata falsa
  de administrador; se añaden anónimo y token inválido. Cada denegación compara además
  hashes del estado persistido; respuestas de error no incluyen datos de perfiles ni tokens.
  Se prueban lecturas directas/joins, RPC privilegiadas, FK/roles manipulados y cuerpos
  suplantados. Las unitarias de los dos casos de uso quedan anticipadas en RED para T031.
- **T030 completada:** migración creada mediante CLI y aplicada exclusivamente al destino
  local comprobado. SELECT permite relación propia o administración activa del tenant.
  `public.list_barbershop_memberships(uuid)` usa SECURITY INVOKER, `search_path=''`,
  EXECUTE solo para authenticated y comprueba administración vigente antes de listar.
  Devuelve únicamente id/user_id/barbershop_id/role/status; no une perfiles ni concede escrituras.

SQL usa roles/claims sintéticos dentro de transacciones que terminan en ROLLBACK; no
acredita emisión JWT. HTTP sí usa Auth real para las siete identidades. La revocación se
confirma mediante COMMIT de la fixture: el mismo JWT pierde lectura/listado en A en la
siguiente solicitud, conserva su relación inactiva y sigue leyendo B como barbero sin
obtener allí listado administrativo. No se cachean permisos en estas comprobaciones.

Reproducción HTTP desde PowerShell, sin guardar secretos en el entorno:

```powershell
$env:BARBERIA_002_URL = 'http://127.0.0.1:54421'
$env:BARBERIA_002_PROJECT_ID = 'app-barberia-002-local'
node --test --test-reporter=tap tests/integration/tenant-foundation/authorization.test.mjs
```

En TAP HTTP hay 345 subcasos: 342 de matriz, una revocación y dos preflight cliente.
Pasan 343; fallan los dos preflight, más el contenedor padre en el total TAP (346/3 fallos).
No se presenta ese exit 1 como suite global aprobada. T031 implementará los listados de
cliente; T032 acreditará el recorrido completo a través de sus ocho operaciones públicas.

## Cambios de pruebas justificados

La expectativa anterior «solo propias = 2» pasa a «propias + listado admin contextual = 3»
para la fixture compartida; es precisamente el permiso nuevo de T030. Ninguna expectativa
de denegación fue relajada. Se añaden cinco assertions de ACL/search_path de la RPC.

El helper de entorno admite ahora entre tres y siete identidades, conserva tres por defecto
y reutiliza el montaje/cleanup privilegiado local. La prueba del runner suponía ausencia de
`authorization.test.mjs`; al existir el archivo dejó de representar ese escenario. Ahora
ejecuta el mismo runner en un directorio temporal propio sin escenarios, con imports de
herramientas resueltos, y sigue exigiendo exit 1/NOT_READY. No se modificó el runner ni se
suprimió su control. Fallo inicial y repetición permanecen registrados.

siete servicios nuevos ajenos a Edge iguales a la referencia; sin redes/volúmenes antiguos

el log activo `t017-serve.log`. Este log y su proceso no se editaron ni detuvieron.

normalizados; no se modificaron registros históricos ni el log activo.
Persisten **nueve avisos moderados npm**, sin remediación ni auditoría npm aprobada.
No se declara completado el aislamiento integral ni T031–T040; tampoco pruebas nuevas de
Android, Google, remoto o cobertura unitaria de los listados aún no implementados.
